# Stepansky Telegram Build Pro Skill

Агентный скил-сет для Telegram-ботов и мини-аппов, у которых **предсказуемое** поведение — для пользователя, для бизнеса и для того, кто дежурит по инцидентам.

*Инструмент, его каталог и все внутренние пути называются `telegram-stack` — именно на это ссылаются `--stack-path`, `STACK_ROOT` и генерируемые адаптеры. Имя репозитория отличается только потому, что GitHub не принимает кириллицу в названиях.*

## Главная идея

**Всё, что может проверить скрипт, не должно оставаться на уровне текста.**

Документация убеждает — код возврата решает. Поэтому набор разделён надвое:

- **Скилы** учат тому, что требует суждения: как вывести структуру меню из бизнес-требований, когда отвечать реакцией, а когда сообщением, где ставить пейволл, какую поверхность выбрать под задачу.
- **Гейты** отказываются пропускать всё остальное: рукописный MarkdownV2, `callback_data` из f-строки, прямой `bot.send_message` в обход шлюза, хардкод токена, хекс-цвет в мини-аппе, недостижимый экран, требование без интерфейса.

Причина такого разделения практическая. Агент (и человек) под давлением сроков договаривается с прозой: «здесь можно и так», «это же прототип». С `exit 1` не договоришься.

Вторая идея: **API Telegram вы не знаете по памяти.** С апреля 2025 по июль 2026 поверхность менялась девять раз. Поэтому первый шаг любой задачи — сверка версии, а на любой вопрос «а есть ли в Telegram метод для X» ответ обязан опираться на загрузку документации в текущей сессии, а не на воспоминание.

## Какие проблемы решает

Не абстрактно, а конкретными механизмами.

### 1. Меню не соответствует бизнесу

**Симптом.** Заказчик просил «оставить заявку и посмотреть статус», а получилось трёхуровневое меню, в котором заявку видно с четвёртого нажатия. Часть требований в интерфейс вообще не попала, и это выяснилось на приёмке.

**Механизм.** Процедура JSA (Job → Surface → Affordance): бизнес-задачи выписываются как «глагол + объект + результат», классифицируются по пяти осям (частота, форма ввода, обратимость, место, объём данных), после чего матрица однозначно назначает поверхность — команда, постоянная клавиатура, инлайн-клавиатура, пагинация, FSM-визард, мини-апп, инлайн-режим, дип-линк, чеклист, эфемерное сообщение. Результат — файл `navigation.yaml`, который проверяется валидатором и **компилируется** в клавиатуры, роутеры, `/help` и диаграмму.

**Что именно даёт валидатор.** Недостижимые экраны, глубину больше двух нажатий, отсутствие выхода, деструктивное действие без подтверждения, переполнение 64-байтного бюджета `callback_data`, коллизии неймспейсов и — главное — **orphan job**: требование, под которое не создан ни один экран. Это единственная автоматическая проверка «мы реализовали то, что просили».

### 2. Сообщения ломаются на реальных данных

**Симптом.** Бот работает на тестах и падает на пользователе с фамилией «Петров-Водкин» или на файле `отчёт_v2.pdf`. Ошибка `can't parse entities`, и не у всех, а у части.

**Механизм.** MarkdownV2 имеет 18 зарезервированных символов и **три разных контекста экранирования** (обычный текст, код, цель ссылки). Поэтому он запрещён линтером, а не «не рекомендован». Взамен два безопасных пути: `H` — подкласс `str` для HTML, экранирующий автоматически при конкатенации, отклоняющий небезопасные URL-схемы и бросающий исключение на `%`/`.format()`; `E` — построитель entity-массива, считающий смещения в **UTF-16 code units** (эмодзи = 2 юнита — то, на чём ошибается любая наивная реализация) и проверяющий, что `custom_emoji` оборачивает ровно один эмодзи.

### 3. Бот молчит, и пользователь не понимает, работает ли он

**Симптом.** Запрос обрабатывается четыре секунды, индикатора нет, пользователь нажимает кнопку второй раз, вы получаете двойную работу и двойное списание. Либо есть «печатает…», но оно говорит только «жив», а не «на каком этапе».

**Механизм.** Presence Protocol: девять канонических состояний (`RECEIVED → QUEUED → STUDYING → WORKING → WAITING_USER → WAITING_HUMAN → DONE / FAILED / CANCELLED`), каждое излучает **три сигнала одновременно**:

- **реакцию на сообщение пользователя** (👀 принято → 🔎 изучаю → ✍️ работаю → ✅ готово) — она видна рядом с тем, что человек отправил, и переживает прокрутку;
- **строку статуса в сообщении бота**, редактируемую на месте, с анимированным кастомным эмодзи и реальным прогрессом `k/n`;
- **правильный chat action** (`typing`, `upload_photo`, `find_location`, `choose_sticker`) с биением каждые 4 секунды, потому что он истекает через 5.

Контекстный менеджер **гарантирует терминальное состояние**. Настоящая ошибка не в отсутствии индикатора, а в ветке `return`, которая оставляет «Работаю…» в чьём-то чате навсегда — `__aexit__` закрывает это структурно, а не дисциплиной.

### 4. Бэкенд непредсказуем и не диагностируется

**Симптом.** «Иногда не отправляется». В логах ничего. `except Exception: pass` в трёх местах. При рассылке один заблокировавший бота пользователь роняет весь батч. Вебхук переотправляется, и заказ создаётся дважды.

**Механизм.** Один шлюз, через который проходит каждый исходящий вызов: лимитер (токенные ведра на чат, на группу, глобально) → попытка → таксономия ошибок → повтор/деградация/исключение, с одной структурной лог-строкой и одной метрикой на вызов. Таксономия отображает **каждую** ошибку API ровно в одно из шести именованных действий, и неизвестный код даёт `ALERT`, а не тихое `IGNORE` — именно этот алерт сообщает вам, что API уехал, раньше, чем это заметят пользователи. Плюс дедупликация по `update_id`, `trace_id` на апдейт, JSON-логи с редактированием по allow-list и фильтром, вычищающим токен даже из текста трейсбека.

### 5. Мини-апп ощущается как чужая веб-страница

**Симптом.** Белая вспышка при открытии. Карусель у края экрана закрывает приложение вместо прокрутки. В тёмной теме нечитаемо. Вёрстка прыгает при открытии клавиатуры. И — отдельно — любой человек может обратиться к API от чужого имени.

**Механизм.** Токены только из `themeParams`; уважение **двух** семейств безопасных зон (устройство и хром Telegram в полноэкранном режиме); `viewportStableHeight` вместо `100vh`; `--edge-guard: 24px`, за который не должен заходить ни один горизонтально-прокручиваемый элемент; `ready()` вызывается **последним**, после первой отрисовки скелетона; хаптика только на подтверждения. Безопасность: HMAC-SHA256 валидация `initData` на сервере при каждом запросе, обмен на короткоживущую сессию, повторная проверка с окном 1 час для всего, что касается денег, и линтер, который валит сборку, если роут читает идентификатор пользователя из тела запроса.

### 6. Бот и мини-апп — два разных продукта с одной иконкой

**Симптом.** В боте статус «В работе», в аппе «Выполняется». Цена в боте `1 200 ₽`, в аппе `1200 руб.`. Правило «срочно только при наличии баланса» реализовано дважды и разошлось. Действие, завершённое в аппе, не оставило следа в чате, и пользователь не уверен, что оно прошло.

**Механизм.** Пять швов, каждый — структурный, а не дисциплинарный. Одна таблица пользователей (`initData.user.id` = `message.from.id`). Один каталог `services/`, который импортируют и бот, и API аппа; `api/` разрешено импортировать только `services/` и `models/` — это проверяется. Один `navigation.yaml`, где маршруты аппа объявлены рядом с экранами бота. Один `copy.yaml` и один `tokens.yaml`. И правило: **действие, завершённое в аппе, обязано оставить сообщение в чате** — с CI-проверкой на это.

### 7. Стикеры используются как контент, а не как система

**Симптом.** Эмодзи вклеены прямо в текст кнопок, выравнивание плывёт, иконки статичны, в тёмной теме выглядят инородно.

**Механизм.** Один набор кастомных эмодзи с `needs_repainting: true` — девять одноцветных глифов, перекрашивающихся под цвет окружающего текста, а значит корректных в светлой теме, в тёмной и в той, которую Telegram выпустит в следующем году. Они используются в **трёх** местах сразу: внутри текста как entity, как `icon_custom_emoji_id` на кнопках (Bot API 9.4+) и как визуальный якорь Presence Protocol. Плюс идемпотентный сборщик набора и офлайн-валидатор форматов.

### 8. Деньги теряются на шве между оплатой и выдачей

**Симптом.** Оплата прошла, товар не выдан. Или выдан дважды. Или `pre_checkout_query` не отвечен, и платёж молча провалился без объяснения пользователю. Или юнит-экономика не сходится, потому что 30% забрал магазин приложений.

**Механизм.** Два закона: ответ на `pre_checkout_query` в пределах 10 секунд с человеческой формулировкой отказа, и запись платежа с уникальным ограничением на `telegram_payment_charge_id` в **Postgres** (не в Redis) **до** выдачи, в одной транзакции с выдачей. Плюс явная машина состояний подписки (`trialing → active → grace → cancelled → expired`) вместо вывода доступа из «последний платёж прошёл». Плюс честная арифметика: Telegram комиссию не берёт, но Apple/Google берут 30% при покупке звёзд с мобильного, а конвертация в TON через Fragment добавляет ещё 2–3% — итого ~32% на мобильном против 3–4% на десктопе, и это должно влиять на то, где вы предлагаете покупку.

## Когда применять

| Ситуация | Почему пригодится |
|---|---|
Новый бот от бизнес-требований | Стадии 1–2 воркфлоу закрывают главный риск: интерфейс, не соответствующий требованиям |
Бот с длительными операциями (ИИ, обработка файлов, модерация, очереди) | Presence Protocol — ядро набора |
Бот + мини-апп в одном продукте | Пять швов сшивки; иначе они разойдутся |
Приём платежей, подписки, кредиты | Идемпотентность и арифметика комиссий |
Бот, которым пользуются больше сотни человек | Лимитер, таксономия ошибок, дедупликация, обработка 403 в рассылках |
Наследованный бот, который «иногда глючит» | `tg_preflight` даёт список нарушений с `файл:строка` за минуту |
Нужна анимированная айдентика | Process Pack: девять глифов, генерируемых скриптом |
Хотите использовать Rich Messages / стриминг / эфемерные сообщения | Единственный известный мне набор, покрывающий Bot API 9.5–10.2 |
Команда работает в разных редакторах | `gen_adapters.py` под восемь харнессов |
Нужны воспроизводимые проверки в CI | Гейты работают без агента |

## Когда НЕ применять

Честно, чтобы не тратить ваше время.

| Ситуация | Что делать вместо |
|---|---|
**Бот из трёх команд без состояния**, например уведомлялка из CI | 40 строк на `aiogram` напрямую. Тридцать инвариантов здесь — избыточная церемония. Возьмите разве что `tg_text.py`, чтобы не сломать разметку. |
**Одноразовый скрипт-рассылка** | Возьмите только лимитер и обработку 403 из `references/gateway.md`. |
**Готовый бот на конструкторе** (Manybot, Salebot, n8n) | Набор про кодовую базу; конструктор кодовой базы не даёт. |
**MTProto/юзербот** (Telethon, Pyrogram, TDLib) | Покрытие только Bot API. MTProto упомянут ссылками, не более. |
**Нужен именно другой фреймворк** | Знание переносится целиком (grammY, PTB, teloxide, Nutgram), но шаблоны и линтер `gateway`/`layers` написаны под Python/aiogram. Порт линтера — работа не на один вечер. |
**Вы против кодогенерации** | Компилятор навигации — центральный механизм. Без него остаётся половина ценности. |
**Не готовы обсуждать структуру меню до кода** | Воркфлоу запрещает писать хендлеры до валидного контракта. Если это неприемлемо, набор будет мешать. |

## Чего этот набор НЕ делает

Раздел важнее, чем список возможностей.

**Не пишет за вас бизнес-логику.** `services/` — пустой каталог. Набор структурирует, где логика живёт, как тестируется и как переиспользуется мини-аппом, но что именно считать «срочной заявкой» — ваше дело.

**Не заменяет чтение документации Telegram.** Наоборот: встраивает обязанность её читать. Лестница эскалации — это маршрут к документации, а не её замена.

**Не гарантирует актуальность.** Гарантирует, что вы узнаете об устаревании: `check_api_version.py` сверяет пин с живым changelog. Пин придётся поднимать руками, читая дельту.

**Не даёт готовых полей Bot API 10.x.** Имена методов и классов 10.1–10.2 взяты из changelog и трекеров, а не из отрендеренного method reference. В `telegram-rich` и `app/tg/raw.py` они помечены символом **✱**, и скилы предписывают загрузить документацию и подтвердить их перед первым использованием. Это осознанное решение, а не заглушка: подсунуть непроверенное имя как достоверное — хуже, чем потребовать проверку.

**Не рисует дизайн.** Девять TGS-глифов — рабочие плейсхолдеры с корректной семантикой движения (циклятся длящиеся состояния, терминальные проигрываются один раз и держат кадр), одноцветные, 339–379 байт. Это не художественная работа. Замените арт, сохранив тайминги.

**Не деплоит.** Даёт чеклист выпуска, health/ready-эндпоинты и решение про `drop_pending_updates`. Ваши Docker, Kubernetes и CD — ваши.

**Не проверяет то, что требует суждения.** Из 30 инвариантов машинно проверяется ~22. Глубина навигации ≤2 нажатий, выбор режима ответа, полнота Presence на всех ветках, конфликты жестов — остаются на человеке и агенте. `tg_preflight` даёт список ручных проверок, но выполнить их должны вы.

**Не тестировался прессинг-сценариями на агентах.** Методика `writing-skills` требует прогонять baseline-тесты на сабагентах, фиксировать формулировки, которыми агент оправдывает нарушение, и закрывать их в таблицах рационализаций. В среде сборки это было недоступно. Таблицы рационализаций написаны от опыта, а не от наблюдения. Дисциплина держится машинно — для проверяемого механически это строже, но **прозаические разделы под реальным агентом не отжаты**.

**Не мультиязычен в шаблонах.** Строки в шаблоне бота и мини-аппа — русские. Структура для i18n есть (`copy.yaml` → генерация в оба слоя), заполнение за вами.

**Не покрывает Telegram Business, Stories, Managed Bots, Guest Mode, Communities как рабочие рецепты.** Они перечислены в карте API со ссылками на точные разделы документации. Рецептов с кодом нет.

## Состав: скилы

`skills/` — десять каталогов. Каждый содержит `SKILL.md` с YAML-фронтматтером (`name`, `description`), у четырёх есть подкаталог `references/` с тяжёлыми справочниками, которые читаются по требованию.

### `telegram` — роутер, 1 026 слов

Точка входа. **С него начинается любая задача.**

- **Шаг 0: сверка версии.** Запуск `check_api_version.py --pinned 10.2`. Если API уехал — прочитать дельту и доложить. Если сети нет — сказать об этом вслух, а не молча предположить.
- **Шаг 1: маршрутизация.** Таблица «задача → подскил». На реальной работе применимы почти всегда несколько; `telegram-ux` + `telegram-text` + `telegram-backend` несущие для любого бота.
- **Шаг 2: воркфлоу.** Запрет прыгать сразу к хендлерам.
- **Инварианты.** Девять самых нарушаемых вынесены в тело, все 30 — в справочник.
- **Лестница эскалации.** Пять ступеней на случай «правила закончились» (см. ниже).

## Пять несущих механизмов

Их стоит забрать даже если вы не возьмёте ни строчки кода.

**1. Контракт навигации.** Меню не вопрос вкуса. Задачи классифицируются, матрица назначает поверхность, YAML проверяется на достижимость, глубину, выходы, подтверждения и orphan jobs, после чего компилируется. Кнопка, которую нельзя привязать к строке контракта, не проходит ревью.

**2. Presence Protocol.** «Печатает…» говорит «жив», а не «на каком этапе». Девять состояний × три канала, с гарантией терминального состояния.

**3. Форматирование — это тип, а не дисциплина.** Не «экранируйте внимательно», а «сделайте так, чтобы экранирование не было вашей задачей».

**4. Один шлюз, одна таксономия, `ALERT` по умолчанию.** Неизвестная ошибка не игнорируется молча — она поднимает алерт. Это способ узнать, что API уехал, раньше пользователей.

**5. Тотальная сшивка.** Бот и мини-апп разделяют `services/`, контракт, копирайт, токены и одну личность — они не могут разойтись по построению. И действие в аппе обязано оставить след в чате.

## Сценарий 1: новый бот с нуля

Опишите задачу обычными словами — роутер подхватится по ключевым словам в описании:

> Нужен бот для приёма заявок на ремонт. Клиент оставляет заявку с адресом и фото, видит статус, может ускорить за деньги. Мастера берут заявки в рабочем чате. Прайс — отдельным экраном с фильтрами.

Дальше по стадиям. Ваши точки контроля:

```bash

python scripts/check_api_version.py --pinned 10.2

# стадия 2 — САМАЯ ВАЖНАЯ: смотрите диаграмму до кода
```

На стадии 2 вы спорите о диаграмме, а не о хендлерах — это в десятки раз дешевле. Если валидатор сообщает про глубину 3, **не добавляйте подменю**: вернитесь к матрице, эта задача хотела команду, инлайн-режим или мини-апп.

## Частые вопросы

**Обязателен ли aiogram?** Нет для знания, да для шаблонов и двух групп линтера. Скилы применимы к grammY, PTB, teloxide, Nutgram без изменений.

**Работает без агента?** Да. Гейты — обычные CLI-инструменты.

**Что если Bot API уедет до 10.3?** `check_api_version` скажет об этом на шаге 0. Дальше вы читаете дельту и либо поднимаете пин, либо явно называете, какие новые возможности решили не использовать. Молча продолжить набор не позволяет.

**Почему MarkdownV2 запрещён, а не «не рекомендован»?** 18 зарезервированных символов × 3 контекста экранирования = отказ, зависящий от данных. Он всегда доезжает до продакшена, потому что в тестовых данных нужного символа нет. Запрет проверяемый, рекомендация — нет.

**Зачем компилировать навигацию, а не писать клавиатуры руками?** Чтобы достижимость, глубина и покрытие требований стали свойствами графа, а не ощущением на ревью. И чтобы `/help` не расходился с реальностью через спринт.

**Можно взять только Presence Protocol?** Да: `templates/bot/app/tg/presence.py` зависит только от `errors.py` и `text.py`. Плюс сгенерируйте глифы.

**Почему `ALERT` для неизвестных ошибок, а не игнор?** Потому что неизвестный код означает, что ваша модель API устарела. Это самый высокосигнальный алерт во всей системе.

**Что делать, если гейт `tests` красный из-за отсутствия pytest?** `pip install pytest pytest-asyncio`. Это правильное поведение гейта, а не поломка.

## Как развивать

Пул-реквесты приветствуются. Что было бы наиболее полезно:

1. **Прессинг-тесты на агентах.** Прогоните задачу с загруженными скилами, зафиксируйте формулировки, которыми агент оправдывает нарушение правила, и добавьте контраргумент в соответствующую таблицу рационализаций. Это единственный пробел в методике.
2. **Подтверждение полей ✱** по отрендеренному method reference, с заменой пометки на ссылку.
3. **Порт линтера** групп `gateway` и `layers` на TypeScript (grammY/Telegraf).
4. **Проверка адаптеров** в реальных Cursor / Windsurf / Aider.
5. **Художественные глифы** вместо плейсхолдеров — с сохранением таймингов и `needs_repainting`.
6. **Рецепты** для Business-аккаунтов, Stories, Managed Bots, Guest Mode.

Правило одно: **всё, что можно проверить машинно, должно попадать в гейт, а не только в текст.**
